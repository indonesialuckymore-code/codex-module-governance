# 裁定请求整理器

只处理原任务窗口的单个阻塞问题。复用 C03 的 `adjudications` 分区，不建立第二本任务账。每个项目只有一个逻辑角色 `CURRENT_ADJUDICATION`。

## 工作顺序

1. 校验 C03 总账及回执，确认原任务、原窗口和当前阻塞状态一致。
2. 若项目还没有裁定角色，先由 C08 连续性控制器从 `CURRENT_CENTRAL` 复制出第一代裁定窗口；不得手工新建平行裁定窗口。
3. 将问题、已知事实、证据引用、受影响对象、候选方案、取舍和延迟后果整理成不可覆盖请求包，只追加到当前裁定窗口。
4. 让中央后台顾问复核请求包；顾问只能推荐现有方案、要求补证或表示没有安全建议。
5. 把顾问意见只返回 Boss，不发送给任务窗口，不改变任务状态、占用或业务对象。
6. Boss 最终决定后，同时生成两份不同回传：原窗口收到完整执行指令；中央只收到任务影响、依赖影响、成立条件和失效条件。
7. 原任务窗口依据 Boss 决定继续处理；C07 不自动派发、不恢复任务、不执行决定。

## 顾问输出要求

- 区分已证实事实、推断和未知项。
- 说明推荐方案、业务作用、主要代价、可逆性和成立条件。
- 不得扩展到请求包之外的对象或公司责任规则。
- 高风险、证据不足或无安全方案时，要求补证或建议暂停，不冒充确定结论。

## 永久边界

- 只有 `codex-module-central` 可以记录 C07 治理材料和 C03 裁定引用。
- 顾问意见只返回 Boss；没有 Boss 决定时，原窗口不能把意见当授权。
- Boss 决定必须返回原任务窗口，不得绕过任务窗口直接改业务。
- 裁定讨论、顾问推理和 Boss 理由留在裁定窗口；中央只读 `central-impact-receipt.json`，不把整段讨论带回中央上下文。
- 裁定窗口不能登记任务、改依赖、派发窗口、验收任务或写 C03；它不是第二中央。
- 不修改任务状态、不创建或释放占用、不创建 TEST、不写业务对象、不启停生产入口。
- 只在仓库外私有目录保存去敏文本和不透明引用；拒绝密钥、Cookie、链接和绝对路径。
