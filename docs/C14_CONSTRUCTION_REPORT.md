# C14 任务双向通信桥施工与验收报告

状态：`DONE`（产品代码、虚构隔离回归和 Skill 结构校验完成）；不代表任何真实项目已经自动收发消息。

## 解决的问题

过去 C08 能把回传票据写入私有事件箱，却没有把“持久入箱”与“中央任务实际被唤醒”分开。中央向任务窗口发送补充指令也没有可消费收件箱和收件确认。因此可能出现两种错误表述：

1. 任务窗口说“已回传”，实际只有本窗口文字或本地票据，中央没有得到可处理提醒。
2. 中央说“已通知任务窗口”，实际没有证据证明任务窗口收到了这项指令。

## 本次新增

- C14 `task-communication-bridge`：唯一的跨 Codex 任务通信执行层；不维护任务详细状态。
- 双向持久信封：任务到中央的回传通知、中央到任务的指令、任务对指令的执行结果各有独立不可覆盖信封和摘要哈希。
- 四段通信状态：`QUEUED`（本地信封已入箱）、`DELIVERED`（Codex 原生消息发送有回执）、`ACKNOWLEDGED`（当前收件任务确认读取）、`APPLIED / REFUSED / BLOCKED`（任务窗口的指令结果）。
- C08 与 C14 对接：回传先由 C08 作为事实源入箱，再由 C14 只把票据指针发送给最新 `CURRENT_CENTRAL`。
- 中央换代重路由：未确认消息在发送前重新解析逻辑中央，不向旧中央盲发。
- `verify-c14.sh` 与 3 项虚构隔离回归：防假确认、中央到任务往返且 C03 不变、中央换代后重定向。

## 运行边界

```text
任务窗口 -> C08 回传票据/事件 -> C14 信封 -> Codex 原生消息 -> 中央确认 -> C08/C06
中央 -> C14 指令信封 -> Codex 原生消息 -> 任务窗口确认 -> 结果信封 -> 中央确认
```

消息正文不携带施工原文。中央只读任务、票据、摘要和验收结论；任务原文仍由 C06 独立验收。C14 不改变 C03、C05、C06、C08 或 C10 的职责。

## 验收门槛

1. 未取得 `RUNTIME_MESSAGE_DELIVERED_AWAITING_ACKNOWLEDGEMENT` 时，中央或任务窗口不能宣称已送达。
2. 未取得 `MESSAGE_ACKNOWLEDGED` 时，不能宣称对方已收到。
3. 无 C08 回传票据、事件、任务身份、窗口代际或摘要哈希时，C14 拒绝把任务文字伪装成回传。
4. 中央指令收发、确认和结果回传全程不改变 C03 任务状态；任何完成、阻塞或验收仍按 C08/C06 进入。
5. 中央从 G1 换为 G2 后，未确认任务消息只可投递和确认给 G2；旧中央不再有确认权。

## Boss 验收方法

1. 在一个虚构项目开中央和任务窗口，向任务窗口发一项 C14 指令。
2. 任务窗口应先显示“已投递、等待确认”，不是“已执行”。
3. 打开任务窗口确认；中央才能看到该指令已被接收。
4. 任务窗口反馈 `APPLIED`、`REFUSED` 或 `BLOCKED` 后，中央应收到一个结果票据指针，不能收到施工原文。
5. 再让任务窗口提交 C08 回传：若不执行 C14 原生投递，中央不得称“已收到”；原生投递且中央确认后才可进入 C06 单槽验收。

## 剩余风险

- Codex 原生消息工具的成功回执证明平台接受了投递；网络延迟、任务被用户暂停或界面被关闭时，最终以 `MESSAGE_ACKNOWLEDGED` 为准。
- C14 不能在没有任何 Codex 任务被执行时自行长期驻留；它通过原生消息唤醒正确任务，并用持久信封避免消息遗漏。
- 真实项目启用前仍需在新的中央和任务窗口做一次不涉及业务写入的端到端冒烟验收。
