# C10 施工报告

## 状态

`DONE`（产品调度合同和项目归属门禁通过；真实业务仍按各任务包施工）

## 当前能力

- 绿/黄/红调度分类和派发准备→真实运行确认两阶段；
- 单任务批准与中央启动图范围化批准；
- 同一波多个合格任务可批量派发，后续波次仍须前置 `DONE` 和 C05 复核；
- 新建和复用任务窗口、最多 3 个 Terra 一级子 Agent及父窗口统一汇总；
- 任务窗口在开始前、发现独立材料时、验收前三次主动判断是否补派；补派只接受同一已批准范围、无共享写入风险且仍有名额的请求；
- 子 Agent 使用结构化回传，父窗口必须完成证据读回、验收覆盖和冲突处理质量闸门后才可进入 C06；
- 派发前绑定 Codex 保存项目，Git 默认标准 worktree；
- 创建后验证项目 ID、运行环境和目录，错误项目或自定义目录不写 C03；
- worktree 路径正确但项目 ID 为空时，对同一任务执行项目本地往返交接并保存修复证据；
- 总账、任务包和运行任务使用同一任务 ID；运行标题固定为 `任务ID｜业务名称｜G代际`，不符时不推进总账；
- 任务回传写入目标为 `CURRENT_CENTRAL` 的持久事件箱，中央换代不要求重开施工窗口；
- 平台不能自动建窗时只生成可复制包，不伪造真实运行成功。

## 本轮问题与修复

现场发现任务虽然拿到了项目引用，但被创建到中央自造的 `/Documents/Codex/.../task-id` 目录，Codex 左栏仍显示在“最近”。本轮把项目归属从提示词升级为 C10 机械合同：派发单保存 `runtimeTarget`，运行确认必须回传相同的保存项目 ID 和标准 local/worktree 目录，否则返回 `NEEDS_REVIEW` 且总账不推进。

真实前向验收又发现第二种平台状态：按正确保存项目直接创建 worktree 后，物理目录和 Git 基线均正确，但应用回读的项目 ID 仍为空。对同一任务执行“交接到项目根目录→交接回原 worktree”后，最终项目 ID、标准 worktree 和 Git 基线同时正确。C10 因此增加可审计的往返修复协议，不靠人工重新建窗。

中央启动图批准必须绑定启动图 ID、SHA-256、波次和获批任务清单；任务不在批准清单中就拒绝，避免把“一次批准”扩大成无限授权。

本次再修复第三种现场问题：任务包名称和 Codex 左栏标题不一致，Boss 无法确认当前任务。现在 C10 在第二阶段同时回读任务 ID、完整标题和代际；任一不符返回 `TASK_IDENTITY_MISMATCH / NEEDS_REVIEW`，C03 保持原状。

本次新增“提速不降质”合同：子 Agent 不再只是初始派发时的静态建议。任务窗口可在原任务中发现可隔离工作后申请补派，但 C10 会机械拒绝范围扩大、共享写入风险、失联窗口和超过 3 个的请求。每名 Agent 必须返回范围、事实、证据、风险和建议；父窗口不得拼接原文，必须形成六类验收覆盖和关键证据读回的质量闸门。C06 同时检查这个闸门，避免任务窗口跳过整合直接申请最终验收。

## 验收

- C10 独立隔离测试覆盖绿黄红、授权、批量范围、项目归属、自定义目录拒绝、运行确认、幂等、失联、初始/运行中子 Agent、结构化回传、父窗口质量闸门和手工降级；
- C09 前向合同检查中央必须一次列全决策和任务，并使用保存项目派发；
- 官方 Skill 结构校验、插件合同和 C01–C13 全回归必须全部通过；
- 真实项目任务前向验收已通过修复路径：最终任务回读到正确保存项目 ID、标准 Codex worktree 和一致 Git 基线；直接创建路径仍可能先返回空项目 ID，不能跳过最终回读。

## 剩余风险

- worktree 只隔离本地 Git 文件，不隔离 Lark Base、AnyCross、数据库、部署或共享账号；C05 仍须实时检查外部对象唯一写入。
- 已经创建在“最近”中的旧任务不会被批量静默迁移；C10 只修复本轮已批准派发且尚未登记成功的同一任务。
