# 安装说明

Boss 已批准将 `0.23.0-rc.1` 作为 GitHub 默认使用版本；下列命令从 `main` 安装新版，不再指向旧标签 `v0.22.0`。保留候选版本号，不把默认选用等同全部环境验收；验收边界统一见[候选版状态](../plugins/codex-module-governance/references/release-status.md)。安装或升级前先备份并核对范围与兼容性。

候选主版本为 `0.23.0-rc.1`，本地更新可带 `+codex.<标记>` 刷新缓存；配置合同仍为兼容的 `0.22.1`，这些不是同一概念。程序更新不自动改全局权限；历史机器维修工具不随产品分发，不用旧安装入口覆盖候选，也不恢复退役自定义权限。

回退必须先列全私有数据根，向 C13 `rollback` 逐个传入 `--private-data-root`。若新版已产生大纲、纠偏、等待、反馈、适配验收或原生交接记录，旧读写器不支持时拒绝降级，当前程序与全部新工作保留。此时先做兼容修复或只读保全，不能恢复旧账本抹掉新工作。该检查只覆盖申报的根及已知格式，不能替代运行中任务停写、全量备份和真实续办验收。

## 新电脑或其他使用者复用：候选发布验收条件

安装插件只复制通用能力，不复制原使用者的项目总账、聊天、账号、凭据和业务资料。朋友使用自己的项目与私有目录；原使用者换电脑接续旧项目须另做私有资料迁移及中央接管，不视为全新初始化。

- 当前验证平台为 macOS；运行脚本需要可用的 Python 3。程序使用 Unix `fcntl` 文件锁，Windows 原生 Python 不属于已支持范围；Linux 或 WSL 也须实测后才能宣称支持。
- 需要 Codex 中可用的原生任务能力、自己的模型使用权限、Git 工具与私有 GitHub 仓库访问权。默认 Terra 不代表任何账号自动获得该模型；不可用时明确报告并让用户选可用模型，不静默冒充。
- 开发及发布验收环境还需安装 `requirements-dev.txt` 中的依赖；不能使用维护者已有虚拟环境代替新环境依赖验证。
- 候选推送后，从明确的远端候选提交干净克隆，只使用版本管理中的文件；不得借用维护者路径、已安装缓存、维修脚本或私有配置。读回安装版本与候选内容一致，稳定标签保持不变。
- 在新的受支持环境中新开任务，确认只有一个中央工作台入口；用虚构项目验证初始化、模型及权限选择、同项目派发、回传和中央交接。保存实际回执，不以提示词或文件存在代替成功。
- 无权限、缺依赖、模型不可用或平台能力缺失时，应明确说明缺项，不能造成半初始化或伪造运行成功。整个验收不创建真实申报、提交或付款。

以上是发布门槛，不是已完成清单。本机临时目录安装与回退测试不能代替远端安装和另一环境验证；未达到门槛前仅作为候选试用，不承诺跨电脑开箱即用。

## Boss 实际怎么安装

前提：电脑已安装 Codex CLI，GitHub 账号已获准访问私有仓库 `indonesialuckymore-code/codex-module-governance`。

```bash
codex plugin marketplace add indonesialuckymore-code/codex-module-governance --ref main
codex plugin add codex-module-governance@qianyi-codex-governance
```

安装后新开一个 Codex 任务，说：

> 初始化 Codex 模块施工控制台。先检查依赖和重复建设，不要施工。

也可以显式调用 `$central-workbench`。这是 Boss 唯一的中央入口；C09 中央控制与 C12 自然语言解析保留为内部协议，不会出现在 `/` 菜单供 Boss 二选一。插件先让用户选择仓库外私有数据目录；不会把工程总账或业务资料写进 GitHub 仓库。

## 本人本地试用后续开发版

试用尚未发布正式标签的后续开发版时，可以直接从本地产品仓库安装，不需要先上传 GitHub：

```bash
codex plugin marketplace add <本地仓库路径>
codex plugin add codex-module-governance@qianyi-codex-governance
```

首次使用在新任务中选择“施工大纲规划”或“中央工作台”；已有项目中央则执行受控交接，不再初始化第二个中央。冻结大纲应转为本期成果、近期任务与必要依赖，远期保持轮廓；同一范围批准不重复询问。正式分享仍固定 Git tag。

## 升级

已有安装若固定旧标签或本地来源，不会因为 GitHub 更新就自动切换。完成备份、停写和兼容核对后，移除当前程序插件和旧 Marketplace 引用，再按默认 `main` 注册安装；不要删除私有总账。需要复现固定版本时，可将 `main` 替换为核实过的提交号。这个操作只处理程序缓存，不处理仓库外私有总账：

```bash
codex plugin remove codex-module-governance@qianyi-codex-governance
codex plugin marketplace remove qianyi-codex-governance
codex plugin marketplace add indonesialuckymore-code/codex-module-governance --ref main
codex plugin add codex-module-governance@qianyi-codex-governance
```

升级前先保留当前可用版本的 Git commit 或 tag；升级后新开任务测试。程序包和用户私有数据分离，升级不迁移、不覆盖工程总账。`scripts/c13-release-validator.py` 可在隔离目录验证安装、备份、升级、失败保全和回退。

## 回退

不要直接卸载新版再安装旧标签。先停下相关写入，备份程序、配置及全部私有数据根；对目标旧程序执行兼容预检。任一根有旧版不支持的新工作时，保留当前程序和记录，先做兼容修复。以下命令先预检全部申报根，通过后才恢复程序；每个根重复传入该参数，不得用空目录代替真实根：

```bash
python3 scripts/c13-release-validator.py rollback \
  --installed-plugin <隔离安装目录>/codex-module-governance \
  --backup <备份目录>/codex-module-governance-<旧版本> \
  --private-data-root <真实私有数据根一> \
  --private-data-root <真实私有数据根二>
```

只申报实际存在的根。回退不删除、不恢复旧总账覆盖新工作；配置也须兼容，不机械恢复旧配置。C13 隔离目录验证不是原生 Marketplace 已切换的证明，真正切换前仍须完成相同兼容检查，切换后新任务读回程序版本并验证可续办。

## 初始化和业务边界

1. 把 `config/module-config.example.json` 复制到**仓库外、未被 Git 管理**的私有位置，并填写 `storage.userDataRoot`。
2. 在 Codex 中使用“启动新项目建档”调用；系统先做只读查重。
3. 只有 Boss 明确批准后，才会在该私有目录创建项目启动卡。
4. C03 再从已存在的启动卡建立 Codex 模块详细账本。首次运行中央工作台的当前任务必须直接登记为 `CURRENT_CENTRAL G1`，不再新建第二个中央。C08 路由激活后，每次 C03 写入还必须带与路由匹配的原生中央任务 ID。
5. C04 只从 C03 的 `PLANNED` 任务生成私有任务合同草案；C04 自身永远不能派发。若 Boss 已批准包含该任务的中央启动图，C05 和 C10 必须引用同一 `bossApprovalRef`，无需再问一次相同范围的任务包批准。
6. Boss 审阅后，C05 读取去敏对象范围：冲突任务进入 `BLOCKED`，安全任务预留全部对象并进入 `READY`；两者都不会实际创建窗口或 Agent。
7. 已有任务窗口回传完成信号后，C06 按批准合同核对成果、适用证据及预定不适用理由，Boss 最终批准后才标记 `DONE`；旧合同保持原标准，占用按原释放流程处理。
8. 原任务窗口需要顾问意见时，C07 只把建议交 Boss；Boss 决定后才生成回原窗口的裁定包，且不自动执行。
9. 窗口或中央失联时，C08 冻结现场并保留占用；新中央经 Boss 授权后只恢复治理控制，不能自动恢复业务施工。
10. C09 首次接收大纲时一次生成中央启动图；Boss 集中回答决策并批准后，图中相同范围不再逐任务重复批准。
11. C10 按当前启动图和执行状态准备派发。新 Git 任务直接使用保存项目的标准 worktree，非 Git 使用 local；字段缺失按[项目归属证据协议](../plugins/codex-module-governance/references/project-association.md)核验，不强制往返。旧封存单按原合同兼容。新任务默认 Terra，可修改；续办保留当前模型。权限默认完全访问，受限模式由 Boss 选择，两者都实际读回。
12. C11 登记外部 Skill 的固定来源、版本、许可证和权限；不自动安装。
13. C12 接收 Boss 业务语言，区分只看、准备和批准执行，再把标准请求交给 C09 唯一中央。
14. 平台不能自动建窗时，C10 `export-fallback` 只生成可复制任务包；Boss 手动开窗时采用所选模型（新任务默认 Terra，可修改），权限默认保留完全访问，也可主动选择工作区受限，同时保留两项证据。在真实任务 ID 与两项证据回传前，任务不会被误记为 `IN_PROGRESS`。

## 当前候选版权限与原生任务设置

- 本版本不会把受限权限写成用户全局默认。新任务默认接受原生完全访问；系统不再创建、安装或依赖自定义权限 Profile。
- 完全访问和 Boss 主动选择的原生 `:workspace` 都必须回传真实运行证据。只有选择受限模式时才要求精确写根与中央私有目录 `DENIED`。
- 自动审核不等于无限授权。启用自动审核时仍应使用交互式批准策略；全局 `approval_policy=never` 不能被当作已通过权限审查。
- 新建、复用和监控任务会使用原生任务工具；任务标题、项目分组、置顶和归档只是方便 Boss 查看，C03/C08/C14 回执仍决定真实状态。
- 升级后旧任务不会热加载新版 Skill。新项目在新任务中初始化；已有项目从当前中央发起 C08 受控换代并核验唯一路由接管，不直接登记第二个中央。模型和权限不因升级强制切换。

项目启动卡不包含任务、窗口、证据或业务数据。C03 总账只保存私有的结构化施工状态和不透明引用；C04 任务包和 C05 占用请求只保存去敏施工合同、对象键及交接引用，不包含真实业务对象。安装完成只说明治理产品可加载，不等于任何真实业务链已上线或验收。
